Fix three defects found by a live packet-lifecycle run against the devnet fleet (issue #565).

**Every default paid write 401'd before the claim was read.** `HttpIlpClient` presented an `ILP-Peer-Id` it held no credential for (the MCP daemon ships `g.toon.client` with an empty `btpAuthToken`). The connector's client edge resolves a PRESENTED identity before it looks at the route and answers `401` when it can't authenticate it, while a request with NO id is anonymous and gets its identity from the payment-channel claim — so presenting an unbacked id is strictly worse than presenting none. The peer id and its bearer secret are now sent as one credential or not at all; the id is still used for the BTP auth frame on the upgrade path, which the connector accepts unregistered. This REMOVES the 401 rather than recovering from it, so it complements #569's `Http401RequiresBtpError` fallback rather than replacing it: that fallback still catches a 401 with any other cause, but it costs a failed round trip per write and can only rescue a client that has a BTP uplink — a proxy-only client had no route to a paid write at all. The MCP daemon additionally defaults `preferBtpForPaidWrites` to `true` whenever a `btpUrl` is configured (override with `preferBtpForPaidWrites` in the config file or `TOON_CLIENT_PREFER_BTP`), since it opens that socket regardless and the live fleet answers an HTTP paid write with `402 requiredTransport: "btp"` anyway.

**`openChannel(destination)` opened the channel against the wrong counterparty.** `resolvePeerId` fell back to "the FIRST negotiated peer" whenever the destination matched no negotiation key — and it never can for a bootstrapped peer, since `BootstrapService` keys results under `nostr-<pubkey16>` while the destination is an ILP address. So `openChannel('g.toon.ario')` opened on-chain against the RELAY's settlement address, and the store's connector then rejected every upload with `F01 — names a channel this connector has no record of`. Counterparty selection is now driven by the destination: the kind:10032 announce that terminates it decides the peer, and that announce's own `settlementAddresses`/`tokenNetworks` synthesize the negotiation when bootstrap never made one (falling through to the x402 greeting as before). The first-peer guess is gone; a single negotiated peer with no announce still resolves, as it did.

**Channel deposits were reported as zero.** The EVM opener never returned the collateral it locked (only the Solana and Mina openers did), so `ChannelManager` tracked — and persisted in the peer binding — `undefined`, and `toon_channels` reported `depositTotal: "0"` / `availableBalance: "0"` on channels the TokenNetwork said were funded. `openEvmChannel` now reports `depositTotal`, `adoptChannel` carries the collateral its binding already recorded, and `setDepositTotal` writes through to the binding so a top-up survives a restart.
